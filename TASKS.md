- [ ] **Bug: `ContentService.UploadToSlotAsync` crashes with a raw ImageSharp exception on a wrong-file-type upload instead of a clean rejection** — found 2026-09-12 while building ludemia's own, separate `CourseContentRepository.UploadFileAsync` (which mirrors this method's pattern for images without calling it). The existing code assumes `Image.DetectFormatAsync` returns `null` for data it can't identify (`if (detectedFormat == null || !allowedTypes.Contains(...)) throw ...`), then only calls `Image.LoadAsync` inside the "recognized" branch. In practice, testing against real non-image uploads (plain text, a PDF) in ImageSharp 3.1.12 showed `Image.LoadAsync` throws `UnknownImageFormatException` — with a raw multi-line "Image cannot be loaded. Available decoders: ..." message — reaching this path anyway, meaning `PersonController`'s/`UserController`'s profile-picture upload almost certainly returns that raw exception text as a 400 body today instead of the intended localized `ContentFileTypeNotAllowed` message, for any wrong-type upload attempt. Likely never caught because the feature's original verification only smoke-tested the happy path + a 401 check, not a wrong-type negative case. **Fix applied in ludemia's own (separate) copy**: attempt `Image.LoadAsync` directly inside a try/catch and use success/failure as the "is this an image" signal (reading the format back off `image.Metadata.DecodedImageFormat` on success) rather than a `DetectFormatAsync` null-check — see `CourseContentRepository.UploadFileAsync`. The same fix has **not** been applied here yet. _Trigger: next time this file is touched, or before relying on that error path for a real user-facing feature._
